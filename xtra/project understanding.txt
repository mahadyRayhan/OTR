## 1. Project Description (use this as context in a new session)

**Project: Adaptive Multi-Agent Bioinformatics Orchestration System**

This is a research-grade multi-agent AI system designed for bioinformatics question answering. The system takes a complex user query, intelligently decomposes it into sub-tasks, routes each sub-task to a specialised agent, and synthesises a final answer — while continuously adapting its behaviour based on the user's evolving intent profile.

---

**Core components and their relationships:**

**Query Decomposer** (`orchestrator/decomposers.py`) — Four strategies of increasing sophistication. Strategy 1: LLM-based (`plan_and_solve`, `llm_compiler`) — probabilistic, generates flat or dependency-aware task lists via Gemini. Strategy 2: `qdmr_rule` — fully deterministic, splits the query into clauses via RST heuristics, classifies each clause into a QDMR operation (SELECT, COMPARATIVE, CODE, etc.), and routes to an agent via a static lookup table. Strategy 3: `coverage` — models the query as a bit-vector of information-need features and selects the minimum set of agents that covers all features (greedy set cover, Chvatal 1979). Strategy 4: `neuro_rule` — LLM resolves coreferences and produces a clean dependency DAG; deterministic QDMR rules then handle agent routing. All strategies produce a `List[TaskNode]` where each node has an agent name, query string, and dependency list.

**User Profiler** (`user_profiler.py`) — Maintains a Bayesian Dirichlet distribution over three response-style dimensions derived from Bloom's Revised Taxonomy: `CONCEPTUAL` (definitions, mechanisms), `PROCEDURAL` (code, implementation), `ANALYTICAL` (comparisons, literature, evaluation). Unlike a simple exponential moving average, the Dirichlet model provides natural annealing (early queries matter more), free uncertainty/confidence tracking via variance, and context-switch detection via KL divergence. When a user's query intent diverges sharply from their settled profile (KL > threshold), a surge weight is applied to update the profile fast. The profiler runs in parallel with decomposition on every query.

**Agent Registry** (`agent_registry.py`) — Formal capability model for all four agents. Each `AgentCapability` declares: what intent tags it handles, which reasoning modes it supports (CoT/ToT/GoT), its maximum reasoning depth, and which agents it escalates to on failure. The registry is injected into every agent call so agents know what alternatives exist.

**Agent Reasoner** (`agent_reasoner.py`) — Wraps every agent call with a configurable reasoning strategy and depth. CoT (Chain-of-Thought) is a single-pass with optional self-refine rounds where the judge's critique text is threaded forward into the next prompt (Madaan et al. 2023). ToT (Tree-of-Thought) generates multiple candidate answers via distinct named approaches in parallel, then selects the best via a mini-judge. GoT (Graph-of-Thought) decomposes the query into sub-aspects, runs them in parallel, and aggregates. Cross-agent escalation is also handled here: on `MISSING_DATA` failure, the reasoner consults the registry and re-routes to an alternative agent rather than looping.

**Adaptive GoT-DAG** (`orchestrator/adaptive_got_dag.py`) — The execution graph. Seed nodes come from the decomposer output. Execution proceeds in topological waves (Kahn's algorithm as a subroutine). After each wave, every executed node is scored by an LLM judge that returns a quality score AND a typed failure mode (`shallow_reasoning`, `logical_error`, `format_error`, `missing_data`, `unknown`). Nodes below the quality threshold are expanded using GoT operators: BRANCH (split into sub-questions), REFINE (deepen the same question, with judge critique threaded into the prompt), AGGREGATE (synthesise multiple results). MISSING_DATA nodes are never expanded — more computation cannot create absent knowledge. The depth budget per dimension is derived directly from the user profile: `depth = base + floor(profile_weight / weight_per_level)`. So if a user has ANALYTICAL=70%, analytical agents get up to 4 reasoning rounds; a PROCEDURAL=20% agent gets only 2. Four termination conditions prevent infinite loops: quality threshold met, depth budget exhausted, quality plateau (delta < epsilon), or absolute expansion budget reached.

**Engine** (`orchestrator/engine.py`) — The pipeline coordinator. Runs profiler and decomposer in parallel. Builds an executor closure (capturing `user_input`, the DAG reference, depth budget, and profile) that the GoT-DAG calls for every node. The closure resolves parent results via `dag._nodes[pid]` for dependency injection, picks the reasoning mode from profile + QDMR op, and calls AgentReasoner. After execution, a global judge scores the final answer. If the score is below `RERUN_SCORE_THRESHOLD`, a `FailureAttributor` LLM call identifies which specific agent produced the weakest sub-answer, and the pipeline re-runs with that agent's dimension depth budget boosted.

**Four agents:** `rag` (RAG-based knowledge retrieval with CoT/ToT/GoT reasoning strategies), `code` (Python code generation and debugging), `scholar` (expert and paper discovery), `cloud` (AWS/infrastructure deployment). Each is a thin async wrapper normalising its output to a plain string.

**Config** (`config.py`) — Active config (`Config` class) for interactive mode. 13 named `BenchmarkConfig` snapshots in 5 groups, each isolating one variable: decomposer (5 variants), DAG builder (topological vs GoT), profiler (on/off), reasoning depth (1/2/3), and full system. `cfg.apply()` pushes a snapshot into the active `Config`. Benchmark runs all questions in sequence per config so the profiler drift is observable.

**Benchmark shape:** For each named config → reset profiler → run all test questions in order → record per-question judge scores. This isolates one variable at a time while keeping profiler evolution intact within a question set.

## 2. How to Build Agent-to-Agent Communication Evaluation

**What "agent-to-agent communication" means in this system**

Communication between agents is not a direct message-passing protocol. It flows through the DAG: when node B depends on node A, node A's result is injected as `context` into node B's prompt by the executor closure. The quality of this communication is therefore measurable as: how much of what A said did B actually use, and did it improve B's answer.

---

**File 1: `communication_log.py` — the instrumentation layer**

Add a `CommunicationLog` dataclass that records one edge-level communication event. Fields needed: `from_node_id`, `to_node_id`, `from_agent`, `to_agent`, `context_passed` (the exact string injected), `context_length`, `from_result_quality`, `to_result_quality`, `wave_number`, `timestamp`. Add a `CommunicationLogger` class with a simple append method and serialisation to JSON. Instantiate one per pipeline run and pass it into the executor closure. Every time the executor resolves parent context for a dependent node, it should log one event before calling AgentReasoner.

---

**File 2: `communication_evaluator.py` — the metrics engine**

Three categories of metrics, each answering a different question:

**Semantic utilisation** — Did agent B actually use what agent A passed? Embed both `context_passed` and `to_node.result` using a sentence-transformer model (e.g. `all-MiniLM-L6-v2` from the `sentence-transformers` library). Cosine similarity between the two vectors gives a utilisation score in [0,1]. A score below 0.3 means the dependent agent largely ignored its context. Also run an LLM judge call with the prompt: *"Given this context from a prior agent, did the following answer make use of it? Score 1-5."* This gives a human-interpretable utilisation rating alongside the vector metric.

**Information gain** — Did the context actually improve the dependent agent's answer? For each dependent node, compare its quality score against the quality score of the same agent run without context (you need a baseline run where dependencies are stripped — the `dag_topological` config already does this since it flattens the graph). The difference is the information gain from the inter-agent handoff.

**Dependency resolution accuracy** — For decomposers that produce placeholder strings like `[result of task 1]`, check whether those placeholders were actually resolved in the final executed query. A simple string scan for unresolved bracket patterns detects failed dependency injection.

---

**File 3: `communication_report.py` — aggregation and output**

Consumes a list of `CommunicationLog` objects from one or more benchmark runs and produces three outputs:

A **per-edge table** — every agent→agent edge that occurred across all runs, with its average utilisation score, average information gain, and resolution accuracy. This immediately shows which handoffs are working (e.g. RAG→CODE with high utilisation) and which are not (e.g. SCHOLAR→RAG with low utilisation, meaning RAG ignores what scholar found).

A **per-config heatmap** — a matrix of agent pairs (RAG, CODE, SCHOLAR, CLOUD) × configs, filled with mean utilisation score. This lets you visually compare whether `neuro_rule` produces better-utilised dependencies than `qdmr_rule`.

A **profiler correlation** — for each communication event, check the user's profile at that moment. If PROCEDURAL is high and the RAG→CODE handoff has high utilisation, that confirms the profile-depth mechanism is working as intended. If CONCEPTUAL is high but CODE→RAG utilisation is low, the system is wasting tokens on a direction the user doesn't need.

---

**How these files connect to the existing system**

The `CommunicationLogger` instance is created inside `_execute_pipeline` in `engine.py` and passed into `_build_executor`. The executor logs one event per dependency resolution. After `got_orchestrator.run()` completes, the logger's events are passed to `CommunicationEvaluator.evaluate()` which computes all metrics and returns a structured report. The report is added to the pipeline's return dict alongside `final_answer` and `judge_score`. In benchmark mode, all per-run reports are aggregated by `CommunicationReport` and written to a JSON file and an optional markdown table.

---

**What the evaluation will tell you**

If utilisation scores are low across the board, the context injection in the executor closure is not working — the prompt structure is burying the context where the model ignores it. If information gain is near zero, the decomposer is creating false dependencies — tasks that could run independently are being unnecessarily serialised. If dependency resolution accuracy is low for `neuro_rule` but high for `qdmr_rule`, the LLM-produced placeholders are not being resolved correctly by `_resolve_dependencies`. These are the three failure modes worth watching.
